# 프론트엔드 코딩 컨벤션

## 1. 기본 원칙

- Vue 2 및 현재 설치된 Vue CLI 5 생태계와 호환되는 문법을 사용합니다.
- `.editorconfig`에 따라 JavaScript와 Vue 파일은 공백 2칸으로 들여씁니다.
- 줄 끝 공백을 제거하고 모든 파일 끝에는 개행을 유지합니다.
- 수정 범위를 작게 유지하고 관련 없는 파일을 포맷하지 않습니다.
- 새 코드는 `plugin:vue/essential`과 `@vue/standard` ESLint 규칙을 따릅니다.
- 비즈니스 규칙이나 화면 동작이 불명확하면 추측해서 구현하지 않고 확인합니다.

## 2. 디렉터리 역할

- 서버 API 함수는 `src/api`에 둡니다.
- 전역 라우트와 내비게이션 처리는 `src/router`에 둡니다.
- 여러 화면에서 공유하는 상태는 `src/store`에 둡니다.
- 재사용 가능한 UI는 `src/components`, 라우트 단위 화면은 `src/views`에 둡니다.
- 이미지와 공통 스타일은 `src/assets`에 둡니다.
- HTTP 공통 설정과 인터셉터는 `src/utils`의 기존 요청 모듈 구조를 따릅니다.

## 3. 명명 규칙

- Vue 컴포넌트 파일명과 컴포넌트명은 `PascalCase`를 사용합니다.
- JavaScript 변수, 함수, 메서드와 모듈 파일명은 `camelCase`를 사용합니다.
- 상수는 `UPPER_SNAKE_CASE`를 사용합니다.
- 이벤트 핸들러는 수행하는 동작이 드러나는 이름을 사용합니다.
- boolean 값은 `is`, `has`, `can`, `should` 계열 이름을 우선합니다.
- API 함수는 대상과 동작이 드러나도록 `get`, `create`, `update`, `delete`, `login`, `logout` 등의 동사로 시작합니다.

## 4. Vue 컴포넌트

- 단일 파일 컴포넌트는 기존 프로젝트 순서에 맞춰 `template`, `script`, `style` 영역을 구성합니다.
- 화면 컴포넌트가 지나치게 커지면 재사용 가능하고 책임이 분명한 단위로만 분리합니다.
- `data`는 함수로 선언하고 컴포넌트가 소유한 상태만 반환합니다.
- 계산 가능한 값은 불필요하게 중복 저장하지 말고 `computed` 사용을 우선합니다.
- 상태 변화에 부수 효과가 필요할 때만 `watch`를 사용합니다.
- 템플릿의 반복 렌더링에는 안정적이고 고유한 `key`를 제공합니다.
- 직접 DOM 조작보다 Vue의 데이터 바인딩과 이벤트 시스템을 사용합니다.
- props를 직접 변경하지 않고 이벤트 또는 로컬 상태를 통해 변경 의도를 전달합니다.

## 5. 상태 관리와 라우팅

- 한 화면에서만 사용하는 상태는 컴포넌트에 두고, 여러 화면에서 공유하는 상태만 Vuex에 둡니다.
- Vuex 상태는 mutation을 통해 변경합니다.
- 비동기 API 호출은 action에서 처리하고 Promise 실패를 호출자에게 전달합니다.
- 라우트 이름은 고유하고 역할이 드러나게 작성합니다.
- 인증이 필요한 화면의 접근 제어는 개별 컴포넌트에 중복 구현하지 말고 공통 라우팅 정책을 우선 검토합니다.

## 6. API와 오류 처리

- API 기본 URL, 서비스 키와 환경별 값은 환경 설정에서 주입하고 새로 하드코딩하지 않습니다.
- API 함수는 요청 구성을 담당하고 화면 표시 로직을 포함하지 않습니다.
- 요청 인터셉터에서는 필요한 공통 헤더만 설정합니다.
- 응답 오류를 정상 응답처럼 숨기지 않고 호출자가 성공과 실패를 구분할 수 있게 전달합니다.
- 사용자 메시지와 개발용 로그를 구분하고 토큰, 비밀번호와 개인정보를 출력하지 않습니다.
- 빈 `catch` 또는 처리되지 않는 `Promise.reject`를 만들지 않습니다.

## 7. 스타일

- 공통 디자인 토큰과 반복 스타일은 기존 공통 스타일 파일을 우선 사용합니다.
- 컴포넌트 전용 스타일은 가능한 한 해당 컴포넌트 범위에 둡니다.
- 기존 화면 전체에 영향을 주는 전역 선택자 추가는 최소화합니다.
- 의미 없는 `!important` 추가를 피하고 선택자 충돌 원인을 먼저 해결합니다.
- UI 변경은 데스크톱과 작은 화면에서 기본 레이아웃이 깨지지 않는지 확인합니다.

## 8. 주석과 문서

- 복잡한 상태 전환, 호환성 제약과 우회 로직처럼 코드만으로 알기 어려운 이유를 설명합니다.
- 코드 동작을 그대로 반복하는 주석은 추가하지 않습니다.
- 기존 주석과 TODO/FIXME는 요청 없이 삭제하지 않습니다.
- 새로운 환경 변수나 실행 전제 조건을 추가하면 관련 문서를 함께 갱신합니다.

## 9. 검증과 완료 기준

- 린트는 파일 자동 수정을 피하기 위해 `npm run lint -- --no-fix`로 실행합니다.
- 번들 구성, 스타일 또는 런타임 의존성에 영향이 있으면 `npm run build`도 실행합니다.
- UI 변경은 관련 라우트에서 로딩, 입력, 성공과 오류 상태를 직접 확인합니다.
- 기존 오류가 있는 경우 수정 파일에서 새 오류를 만들지 않았는지 별도로 확인합니다.
- 검증 실패가 기존 환경 문제인지 변경으로 인한 문제인지 구분해 보고합니다.
